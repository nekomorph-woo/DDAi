# _prd.md 模板

PRD 是讨论的固化，不是填表。本骨架**按需增删**——小项目（feat-s）可只写需求侧 3 节 + 技术决策；大项目（feat）展开全部 9 节。所有内容用完整句子写，DO NOT 填占位符。

## 边界原则

`_prd.md` 容纳"方案意图级"内容，不抢 `_design`/`_define` 的活：

| `_prd.md` 该有（意图级） | 留给下游 |
|---|---|
| 核心技术选型 + 不选 X 的原因 | 模块接口签名（`_design`） |
| 关键子系统候选方案探讨 | 路由表 / 启动流程 / 目录树（`_design`） |
| 概念数据模型（实体关系轮廓） | 字段级 schema（`_design`） |
| 子系统职责交互意图 | 接口契约（`_design`） |
| 粗粒度成功标准 | 精确验收清单（`_define`） |

## 骨架

```markdown
---
status: draft
system-name: <推断的系统名，如 feat-smart-home>
changed: 初始版本
---

# <项目名> PRD

> Brief（3-5 行 blockquote，概括项目是什么、解决什么问题、核心技术方向）

## 背景与动机

<完整句子，说明为什么做这个项目、解决什么问题。如"团队在局域网内缺少轻量的文件共享方式，现有 IM 工具过重且依赖外网，需要一个零部署成本的局域网协作工具">

## 目标与非目标

### 目标
<正向目标，完整句子，如"提供局域网内即开即用的聊天和文件共享能力，无需安装客户端">

### 非目标
<明确不做什么，完整句子，负向界定范围。如"不做跨互联网的远程访问"、"不做多人群视频通话"、"不做复杂的组织架构管理">

## 用户故事与场景

### 场景 1：<标题>
<完整句子描述谁、何时、做什么。如"团队成员在会议室用手机扫码连入，发送会议文件给所有人">

## 技术决策与方案探讨

每个决策点标注三态：已讨论清楚用 ✅，仍在权衡用 🟡，完全未决移到"开放问题"。

### ✅ 已定：<决策标题，如"文件传输走 P2P，不走服务端存储">
<完整句子说明决策 + 原因 + 不选其他方案的理由。如"文件传输采用 WebRTC P2P，服务端只存元信息不存文件本体。原因：局域网内 P2P 带宽充足，服务端不背存储成本。不选服务端中转：服务端要扛磁盘和带宽，违背轻量定位">

### 🟡 探讨中：<决策标题，如"消息通信方式">
<列候选方案 + 利弊 + 当前倾向。如"候选 A（WebSocket）：实时性好，但要维护长连接。候选 B（SSE + 轮询）：实现简单，但延迟偏高。倾向 A，单聊天室场景实时性优先">

## 概念数据模型

<核心实体关系轮廓，ASCII 图，非字段级 schema。如：>

\`\`\`
用户 ──发布──→ 文件公告 ──P2P传输──→ 下载记录
                                  ↑
                              消息（聊天室）
\`\`\`

## 关键子系统设计意图

<各子系统职责与交互意图，非接口签名。如"Server Runtime：承担中心服务，管理设备接入和元信息存储。Client UI：浏览器端，提供聊天和文件操作界面。Admin UI：管理台，负责设备管理和系统配置">

## 约束

<技术 / 业务 / 时间 / 安全方向，完整句子。如"必须在纯局域网运行，不依赖任何外网服务"、"Windows 机器作为服务端，其他设备浏览器访问">

## 成功标准

<粗粒度成功样子，完整句子，精确清单由 _define 细化。如"团队成员能在 30 秒内完成文件发送到全员的操作"、"服务端启动到可用不超过 5 秒">

## 开放问题

- <未决决策，完整句子，如"是否需要支持断点续传，还是首次版本只做完整文件传输">
```

## 三态决策标记说明

"技术决策与方案探讨"章节用三态标记区分决策成熟度：

| 标记 | 含义 | 写法 |
|------|------|------|
| ✅ 已定 | 讨论清楚，拍板 | 决策 + 原因 + 不选其他方案的理由 |
| 🟡 探讨中 | 有多个候选，仍在权衡 | 候选 A / 候选 B + 各自利弊 + 当前倾向 |
| ❓ 未决 | 完全没头绪 | 移到"开放问题"章节 |

这避免了"列举一堆候选方案又不下结论"或"直接拍板不记录取舍"两个极端。
