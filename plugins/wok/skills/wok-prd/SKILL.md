# PRD 撰写

撰写结构化 PRD，作为 wok 管道的需求入口。PRD 容纳"是什么、为什么、怎么做、有哪些可做的方式"的讨论结论，是后续 wok-idea（路线图规划）和 wok-define（需求细化）的输入。

支持两种模式：从零讨论（两阶段），或把外部 PRD 转换为标准骨架。

**术语**："finding"指广义探索（代码库现状、业务背景、技术方案调研），非特指 wok-findings 技能。

## 快速开始

1. 判断模式：用户提供外部 PRD 文件路径 → **模式 B**（转换）；否则 → **模式 A**（从零讨论）
2. 生成 system-name（wok-prd 是管道最前端，新建目录——详见下方"system-name 生成"）
3. 模式 A：阶段 1 探索（禁止落盘）→ 阶段 2 成文
   模式 B：读外部 PRD → 归化为标准骨架
4. 产出 `_prd.md`（路径见下方约定）

### system-name 生成（新建，非解析）

wok-prd 是管道最前端入口——`.wok-plans/<system-name>/` 此时尚不存在，wok-prd **生成**新 system-name 并创建目录。DO NOT 调用 resolve-system-name.sh——那是下游 SKILL（wok-define / wok-odyssey 等）处理**已存在**系统时解析缩写/phase 用的，wok-prd 是新建，无目录可解析。

| 步骤 | 动作 |
|------|------|
| 提取关键词 | 从 PRD 内容/讨论提取核心词（如"智能家居"→ smart-home） |
| 推断前缀 | 多模块/多阶段 → `feat-`；单模块/小功能 → `feat-s-`；默认 `feat-` |
| 组合候选 | `<前缀>-<关键词>`（如 feat-smart-home） |
| 冲突检查 | 检查 `.wok-plans/` 下是否已有同名目录（`ls .wok-plans/`）；同名则追加后缀或让用户改 |
| 用户确认 | 展示候选，用户确认后创建 `.wok-plans/<system-name>/` |

默认推荐 `feat-`（PRD 通常意味着完整需求）。

### 路径约定

| 场景 | 产出物路径 |
|------|-----------|
| 大功能 | `.wok-plans/feat-<关键词>/_prd.md` |
| 小功能 | `.wok-plans/feat-s-<关键词>/_prd.md` |

`_prd.md` 是系统级文档，与后续 `_roadmap.md`（如有）同级，不进入 phase 子目录。

## 模式 A：从零讨论

### 阶段 1：探索（禁止落盘）

> **📝 文风要求**：探索讨论用完整句子表达（不写电报体）。完整规范见 `skills/_shared/doc-writing-style.md`。

探索范围（广义 finding）：

| 探索维度 | 工具 | 用途 |
|----------|------|------|
| 代码库/文档现状 | look（quick/medium/deep） | 理解已有代码结构、约束、组织模式 |
| 技术方案调研 | WebSearch / web-search-prime / web-reader | 搜同类方案、技术选型、最佳实践、竞品 |

与用户实时讨论探索发现，逐步明确四类问题：

- **是什么**：要做什么，核心场景是什么
- **为什么**：动机、价值、要解决的问题
- **怎么做**：技术决策、架构方向、关键选型
- **有哪些可做的方式**：候选方案、利弊权衡、当前倾向

**禁止落盘**：阶段 1 DO NOT 调用 Write/Edit，所有探索结论走控制台输出。这是硬约束——强制充分讨论后再固化文档，防止过早收敛到文档骨架（电报体的根源之一）。

### 阶段 2：成文

把阶段 1 的讨论结论整理为结构化 `_prd.md`（9 节骨架见 [reference/prd-template.md](reference/prd-template.md)）。

## 模式 B：外部 PRD 转换

用户指定外部 PRD 文件路径时进入（如和 ChatGPT 讨论产出的文档、历史 PRD）。

1. 读外部 PRD 文件
2. 分析其结构（用了哪些章节、覆盖哪些维度）
3. 对照 9 节骨架映射：
   - 已有内容 → 映射到对应骨架章节，用完整句子重写（外部 PRD 常有电报体）
   - 缺的维度 → 标注"待补充"或基于现有内容推断补齐
   - 实现级细节（字段级 schema、路由表、目录树）→ **转换或剔除**，不在 `_prd.md` 展开（`_prd.md` 只到方案意图级，实现级留给 `_design` 阶段重新设计；DO NOT 留指针指向管道外的原始文档）
4. 产出标准 `_prd.md`，放入 `.wok-plans/<system-name>/_prd.md`
5. 原始外部 PRD：用户自行处理（不归档）。后续 SKILL 若需参考原始文档的细节，由用户或编排者（wok-odyssey）**显式指定路径**——`_prd.md` 是显式输入，不自动消费，不留指针

## 验证门

展示 `_prd.md` 摘要，用户确认后更新 `status: approved`。

```
## ✅ PRD 撰写完成

**产出**：<system-name> PRD
**模式**：从零讨论 / 外部转换
**覆盖**：<9 节中实际写了哪几节>
**待补充**：<标注"待补充"的节，无则写"无">
**下一步**：/wok-idea（规划多阶段 roadmap）/ /wok-define（直接细化需求）
```

## 反模式

- **落盘（阶段 1）**：阶段 1 禁止写入任何文件到磁盘。所有探索结论走控制台输出。（阶段 2 才写 `_prd.md`）此约束纯指令，无 hook，复用 look 已验证模式。
- **越界（阶段 1）**：探索范围限定用户指定目标，不扩展到无关模块
- **照抄模板**：`_prd.md` 骨架按需增删，写完整句子，DO NOT 填占位符
- **抢下游的活**：`_prd.md` 只到方案意图级——不写模块接口签名/字段 schema/路由表（留给 `_design`）、不写精确验收清单（留给 `_define`）

## 约束

- **禁止落盘是阶段 1 硬约束**：纯指令，无 hook
- **骨架非强制**：9 节按项目规模增删，小项目可只写需求侧 3 节 + 技术决策
- **意图级边界**：`_prd.md` 容纳"方案意图"，精确设计留给 `_design`/`_define`
- **模式 B 守意图级边界**：实现级细节（schema/路由表）转换或剔除，DO NOT 留指针指向管道外原始文档；后续若需参考原始文档由用户或编排者显式指定
- **模式 B 完整句子重写**：外部 PRD 常有电报体，转换时用完整句子重写，DO NOT 照抄片段
