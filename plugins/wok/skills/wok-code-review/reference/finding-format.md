# Finding 输出格式

所有 agent 的输出 finding 必须严格遵循此格式。

> **📝 文风要求**（完整规范见 `skills/_shared/doc-writing-style.md`）：
> 1. 写完整句子——`title` 作为标题可简洁，但 `原因` 和 `修复方案` 必须是完整句子（有主语、有动作），不写电报体
> 2. 术语首次出现就通俗解释（严重度 emoji 含义见下）
> 3. 一条 finding 内部逻辑连贯：现象（title）→ 为什么是问题（原因）→ 怎么改（修复方案）

**严重度标记含义**：
- 🔴 Blocking（阻塞级）：会导致功能中断、数据丢失或安全漏洞，必须修复才能继续
- 🟠 Severe（严重级）：影响功能但有临时规避路径，应尽快修复
- 🟡 Advisory（建议级）：代码质量、可维护性或优化建议，不阻塞，按需采纳

## 标准格式

每条 finding 占连续 3 行，finding 之间空一行：

```
[<severity>] <file>:<line> — <title>
  原因: <why>
  修复方案: <how>
```

**完整例句**（按此句式填充真实内容，不要照抄文字）：

```
[🔴] src/auth/login.ts:42 — 登录成功后未签发刷新令牌
  原因: 当前实现在用户登录成功后只签发访问令牌（access token），遗漏了刷新令牌（refresh token），导致访问令牌过期后用户无法自动续期，必须重新登录。
  修复方案: 在 signLoginResponse 函数内、签发访问令牌之后，调用 issueRefreshToken(user.id) 生成刷新令牌，并一并写入响应体的 tokens 字段。
```

注意 `原因` 和 `修复方案` 都是完整句子，说清了"现状是什么"和"在哪里、改成什么"，而不是"未签发刷新令牌"这种名词堆砌。

## 字段规范

| 字段 | 类型 | 约束 |
|------|------|------|
| `severity` | `"🔴"` / `"🟠"` / `"🟡"` | 严格使用 emoji，不使用文字 |
| `file` | 相对路径 | 相对于项目根目录 |
| `line` | 正整数 | 文件级问题使用 `file` |
| `title` | 字符串 ≤60 | 标题性质，可简洁概括问题，不含换行 |
| `原因` | 字符串 | **完整句子**，说明"现状是什么、为什么会出问题" |
| `修复方案` | 字符串 | **完整句子**，具体可执行——给出代码片段或明确步骤，说清"在哪里、改成什么" |

## 扩展字段

在 `修复方案` 行之后追加（可选）：

| 字段 | 适用 agent | 格式 |
|------|-----------|------|
| `优化维度` | code-reviewer, silent-failure-hunter, type-design-analyzer, pr-test-analyzer | `  优化维度: <simplify 触发标记>` |
| `来源` | 所有 agent | `  来源: <agent 名称>` |

## 空结果哨兵值

无 finding 时统一输出：

```
[OK] 无问题
```
