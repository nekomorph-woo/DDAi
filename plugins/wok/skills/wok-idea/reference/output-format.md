# 路线图输出格式

> **📝 文风要求**（完整规范见 `skills/_shared/doc-writing-style.md`）：
> 1. 写完整句子——每个 feature 和 phase 都用完整句描述它做什么，不写名词堆砌
> 2. 术语首次出现就通俗解释（发散/侦察轨道、phase、P0/S/M 等见下方）
> 3. 简写要展开：P0/P1/P2、S/M/L 首次出现注明含义

## 目录结构

```
.wok-plans/<system-name>/
├── _roadmap.md                    ← 本文件
├── p1-<phase-name>/              ← 后续各 phase 管道循环在此创建
└── p2-<phase-name>/
```

## _roadmap.md 模板

```markdown
---
status: draft
intent: decision
scope: global
depends: []
changed: 初始版本
---

> **做什么**：规划 <项目> 的功能路线图（按阶段拆分要做的功能）
> **怎么做**：双轨探索（发散轨道基于现有知识头脑风暴；侦察轨道通过外部搜索收集灵感）→ 精选 → 按版本阶段分组
> **阻塞**：无

## 项目上下文

<用 1-2 句完整话描述这个项目是什么、解决什么问题，如"一个面向个人开发者的时间追踪工具，帮助用户记录花在每个项目上的时间">

## 发现的 Feature

<用完整句子列出探索中发现的所有候选功能，每个标注来源（发散/侦察）和复杂度评估，如"Markdown 任务笔记（发散，S 简单）"、"GitHub 集成自动导入 issue（侦察，M 中等）">

## 精选 Feature

### [DECISION] <feature 名称，用一句话写清它做什么>

优先级：P0（必须做）/ P1（重要）/ P2（可选）—— 选一个
依赖：<无，或用完整句写清依赖哪个其他 feature，如"依赖'Markdown 任务笔记'先落地">

## 路线图

### p1-<phase-name> — <这个阶段的主题，如"核心任务管理">

目标：<用完整句描述本阶段交付的端到端能力，如"用户能创建、编辑、完成任务，并按项目归类">
模块预估：<N> 个

...

### p2-<phase-name> — <主题>
...
```

## 验证门输出

确认路线图后展示：

```
## ✅ 验证门

**产出**：<项目> 功能路线图，<N> 个 phase，<M> 个精选 feature
**决策**：<关键分组决策>
**阻塞**：无
**下一步**：确认后创建 `.wok-plans/<system-name>/p1-<phase-name>/` 目录，对 Phase 1 执行 /wok-define
```

## 约束

- **DO NOT** 使用缩写标记（如 `D1`、`D2`），必须使用完整 `### [DECISION]` 格式
